# Changelog

Notable changes to chrome-lens-search.

## Unreleased

- Fixed: an upload that never redirects is no longer mistaken for a results page. The check scanned the whole URL for `lens`, and the upload endpoint is itself on `lens.google.com` — so when the POST came back without a redirect, the `req` backend parsed the *upload response* as if it were results, then re-fetched the endpoint and took an HTTP error as the failure instead of the real one. Results URLs are now judged by host and path.
- Fixed: a consent/`sorry` interstitial no longer ends the browser's address-bar poll. Those URLs carry the real destination in a `continue=` parameter, so the substring scan matched the word `lens` inside it and handed back the interstitial as the results URL; the poll now waits through the hop for the actual results page.
- Fixed: the browser's wait-for-tiles check recognises Google's non-`.com` domains. It tested each link for the literal string `google.com`, so on `google.de`, `google.co.uk` or any other country domain the page's own nav and footer links counted as product tiles — the wait was satisfied immediately and the harvest ran before a single tile had rendered. It now matches hosts on label boundaries, like the rest of the library.
- Fixed: an anchor with an empty `aria-label` keeps its own text. Google emits blank labels on image-wrapper tiles, and the HTML parser took them literally and dropped those matches outright — while the browser harvest, where an empty string is falsy, kept them. The two paths agree again.
- Fixed: concurrent result-cache writes no longer collide. `_cache_write` runs outside the module lock and its temp file was named only for the process, so two threads looking up the same image shared one path and could publish a half-written entry. Temp files are also cleaned up when the rename loses a race, instead of accumulating in the cache directory forever.
- Fixed: a URL's host is read without its port or userinfo, so Google's own links are recognised on a host like `www.google.com:443`. Carrying the port along defeated the Google check (it anchors on the end of the host), so such a link counted as a merchant match and its `/url?q=` wrapper was never unwrapped — publishing Google's redirector as the product URL. The port/userinfo also leaked into the user-facing `Match.domain`.
- Fixed: a bare merchant host no longer survives as a *product title*. `Amazon.com`, `thepremierstore.com (+1) - …` and similar tiles passed straight through cleaning, and because titles are frequency-ranked, a few same-merchant tiles were enough for a bare domain to outrank the real product and become `top_title`. The anchors themselves are still returned as matches — only the ranking screens them out.
- Fixed: Google's result breadcrumb no longer leaks into a title. Aria-labels flatten to things like `Nike Killshot 2 Women's Shoes Nike https://www.nike.com › shoes`; everything from the URL on is chrome, and `›`/`»` now count as separators alongside `·`/`|`.
- Fixed: the cookie jar keeps only real Google cookies. The filter scanned each cookie's domain for the substring `google`, so cookies set by unrelated hosts that merely contain the word (`notgoogle.com`, `google.com.cheap.example`) were written into the jar. It now matches on label boundaries, the same rule link classification uses.
- Fixed: the cookie jar is written atomically (write-then-rename, as the result cache already did). Writing in place meant a crash or a full disk mid-write left a truncated, unloadable jar — taking out the fast path that the run was only meant to refresh.
- Fixed: an image URL that answers `200` with an HTML error page is rejected instead of being uploaded to Lens as a JPEG. Google found nothing in it, so a dead link surfaced as a bare "no results" rather than a download failure. Untyped and `application/octet-stream` bodies still go through — plenty of CDNs serve real images that way.
- Fixed: the visible-window retry can no longer make a browser lookup *worse*. When a headless pass came back degraded, the retry's result overwrote it unconditionally — so on a display-less box (where the visible window can't open at all) or when Google answered the second upload with an interstitial, anchors the first pass had already harvested were thrown away and the lookup returned no results. The retry is now kept only when it rendered a real page or harvested more.
- Fixed: `_is_external` judges a host by its labels instead of scanning it for a substring. Google's own links were counted as merchant results on every country domain except `google.com`/`google.co.*` (`google.de`, `google.fr`, `google.it`, …), which both fills `matches` with Google's own chrome and fools the `req` backend's "enough external anchors?" gate check into trusting a gated page; in the other direction, a real merchant host that merely *contained* a Google name (`notgoogle.com`, `mygstatic.com`) was silently dropped.
- Fixed: **lookups work again.** Google retired `www.google.com/searchbyimage/upload`, which now answers 404 for every upload — both backends failed on every image. Uploads go to Lens' own endpoint (`https://lens.google.com/v3/upload`) instead.
- Fixed: the browser backend uploads by submitting an in-page multipart form rather than calling `fetch`. The upload endpoint is on `lens.google.com` while Google lands the session on `www.google.com`, so the `fetch` was cross-origin and its response came back CORS-opaque (`TypeError: Failed to fetch`); a form submission is a navigation, which CORS doesn't apply to.
- Fixed: the browser backend no longer throws away every merchant link on a page where Google wraps its outbound links (`google.com/url?q=<merchant>`). Those wrappers were only unwrapped on the `req` path, so the browser pass — the self-healing fallback — judged each wrapped link by `google.com`'s host and discarded it, reporting no matches for a page full of products. Its wait-for-tiles check was blind to the same wrappers and burned the full timeout before harvesting.
- Fixed: a blank `GLENS_BACKEND` (`-e GLENS_BACKEND=` in a container, an empty line in a `.env`) is treated as "not configured" and falls back to `auto`, like every other `GLENS_*` default. It previously became an empty backend that failed validation on every lookup, raising `ValueError` from `search()` and exiting 2 from the CLI.
- Fixed: `warmup(force=True)` (and `glens warmup --force`) reports failure when the re-mint fails. It only checked whether *a* jar existed afterwards, so the stale jar it was asked to replace counted as success — telling a deploy or CI check the session had been refreshed when it hadn't.
- Fixed: `_unwrap_google_redirect` only unwraps Google's own redirect wrapper; a merchant URL with its own `/url?q=` route keeps the link that was actually harvested.
- Fixed: a merchant link is no longer dropped when it carries a Google token in its path or query (an affiliate tag like `?utm_source=google.com`, a `&url=` redirect target, a `ved` param). External links are now judged by their host, not by a substring scan of the whole URL.
- Fixed: `status()` now reports `jar_age_seconds` as `None` for a jar that has no `minted_at` timestamp (for example, one copied from another machine), instead of a bogus multi-decade age.

## 0.1.0

First public release.

- Google Lens visual product search over plain HTTP: image in, exact product titles + merchant links out (not just OCR).
- Fast/slow hybrid: one browser run mints a Google session, then every lookup runs over plain `requests` (~2s) with no browser in the hot path. Self-heals when the session goes stale.
- Python API (`import glens`): `search`, `search_many`, `warmup`, `status`, plus the `LensResult` and `Match` dataclasses.
- `glens` command-line tool with `search`, `warmup`, and `status` subcommands, JSON output, and scriptable exit codes.
- Opt-in result cache and best-effort language preference.
